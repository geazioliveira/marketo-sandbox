# Glossário

O vocabulário do marketo-sandbox, no sentido em que este repositório usa cada palavra. A prosa é pt-BR. Identificadores, tokens e nomes de arquivo ficam em inglês, como diz o [guia do Context Mesh](../README.md#idioma-e-tokens). Cada termo aponta para onde é definido ou usado.

## O mock e o domínio

- **asset.** A Asset REST API do Marketo, sob `/rest/asset/**` (`README.md:46-48`). Todo o código gerado fica em `src/asset/`, e o Swagger de entrada se chama `docs/marketo-swagger-asset.json`.
- **código gerado.** As três pastas que os geradores emitem: `src/asset/asset-definitions/`, `src/asset/resources/` e `src/asset/asset-mocks/` (`README.md:53-57`). São commitadas e não se editam à mão ([ADR 0004](../decisions/0004-swagger-as-single-source-with-committed-generated-code.md), [A fronteira do código gerado](patterns/generated-code-boundary.md)).
- **consumidor.** Um cliente da API do Marketo que roda os próprios testes contra o mock. O primeiro é o lite-campaign ([project intent](../intent/project-intent.md#declaração-de-intenção)).
- **definição.** Uma entrada de `definitions` no Swagger. São 255, e 53 delas são `ResponseOf*`. O gerador de definições lê `definitions` (`scripts/generate-marketo-definitions.py:174`) e emite cada uma como interface TypeScript em `models/`, `requests/` ou `responses/`, pela terminação do nome (`scripts/marketo_codegen.py:41-46`). "DTO" é a definição vista do código ([ADR 0006](../decisions/0006-dtos-as-typescript-interfaces.md)).
- **envelope.** A forma `{errors, requestId, result, success, warnings}` das respostas `ResponseOf<X>` (`src/asset/asset-definitions/responses/response-of-snippet-response.ts:4-10`). O nome vem do comentário do gerador de factories (`scripts/generate-marketo-factories.py:30`), que fixa `success: true`, `errors: []` e `warnings: []` (`:31-36`). Um item de `errors` é `{code, message}` (`src/asset/asset-definitions/models/error.ts:1-10`). Dos 220 métodos de service em `src/asset/resources/*/*.service.ts`, 186 devolvem um envelope, e os outros 34 devolvem respostas como `DeleteResponse` e `ModelResponse`.
- **factory.** Uma função `makeX(overrides)` em `src/asset/asset-mocks/factories/`, uma por definição, que devolve um `X` preenchido pelo faker (`scripts/generate-marketo-factories.py:215-223`). Uma propriedade `$ref` chama a factory aninhada (`scripts/generate-marketo-factories.py:107-112`) ([Factory com overrides](patterns/factory-with-overrides.md), [ADR 0007](../decisions/0007-faker-factories-with-overrides-and-seed.md)).
- **folder.** A pasta onde um asset do Marketo vive: `{id, type}`, com `type` igual a `'Folder'` ou `'Program'` (`src/asset/asset-definitions/models/folder.ts:1-12`). Um program também serve de folder.
- **gerador.** Um dos três scripts `scripts/generate-marketo-{definitions,resources,factories}.py`, com a base comum em `scripts/marketo_codegen.py`. Cada um tem um modo `--check`, que compara o commitado com o que ele emitiria (`npm run check:<alvo>`, `package.json:11-18`). Hoje o de definições e o de factories escrevem nas pastas antigas, `src/asset-definitions/` e `src/asset-mocks/`, e o de resources emite imports para elas (#7) ([Gerar e conferir](patterns/generate-and-check.md)).
- **mock.** Este serviço: um servidor HTTP local, sem credenciais, gerado do Swagger, para desenvolver e testar consumidores. Não é uma instância Marketo ([project intent](../intent/project-intent.md#tipo-de-projeto)).
- **módulo de recurso.** O trio controller, service e módulo Nest de uma tag do Swagger, em `src/asset/resources/<tag-em-kebab-case>/`, com o nome da tag em PascalCase (`scripts/generate-marketo-resources.py:224-241`). Uma tag "(New)" ganha o sufixo `-new`, como `emails-new` (`scripts/marketo_codegen.py:23-27`). São 23, importados pelo `AssetResourcesModule` (`src/asset/resources/asset-resources.module.ts:26-51`) ([A forma de um módulo de recurso](patterns/resource-module-shape.md), [ADR 0005](../decisions/0005-nestjs-express-one-module-per-tag.md)).
- **operationId.** O identificador de uma operação no Swagger. Vira o nome do método no controller e no service, como `getSnippetByIdUsingGET` (`scripts/generate-marketo-resources.py:114` e `:145`).
- **override.** O `Partial<X>` que uma factory recebe e espalha por último, por cima dos valores do faker (`src/asset/asset-mocks/factories/snippet-response.ts:5-19`). Serve para fixar só o campo que importa: `makeSnippetResponse({ status: 'draft' })`.
- **program.** Um programa do Marketo: `ProgramResponse`, com `type` igual a `default`, `event`, `webinar` ou `nurture`, e `status` igual a `locked`, `unlocked`, `on` ou `off` (`src/asset/asset-definitions/responses/program-response.ts:5-6`).
- **requestId.** O id de requisição de todo envelope, no formato `e42b#14272d07d78`. O mock o gera com `mockRequestId()` (`src/asset/asset-mocks/request-id.ts:3-8`).
- **seed.** O número que fixa o faker: `MARKETO_MOCK_SEED`, com a data de referência em `MARKETO_MOCK_REF_DATE` (`src/asset/asset-mocks/seed.ts:11-23`, `README.md:67-77`). O README promete que a mesma requisição devolve o mesmo payload entre reinícios (`README.md:69-70`). O `seedMockData()` roda uma vez, antes de o app subir (`src/main.ts:8`), então a promessa vale para a mesma sequência de chamadas: medido na #4, duas chamadas seguidas à mesma factory depois do seed devolvem payloads diferentes, e só a primeira se repete depois de semear de novo. Sem seed, as respostas são aleatórias, e `MARKETO_MOCK_SEED=0` também conta como sem seed, porque `Number(...) || undefined` descarta o 0 (`seed.ts:12`).
- **snippet.** Um asset do Marketo com `status` igual a `approved` ou `draft`, um `folder` e um `workspace` (`src/asset/asset-mocks/factories/snippet-response.ts:9-17`). Tem operações de aprovar o rascunho, clonar e conteúdo dinâmico (`src/asset/resources/snippets/snippets.controller.ts:33`, `:40` e `:79`).
- **Swagger.** Dois sentidos. Sem qualificação, "o Swagger" é o primeiro.
  1. O documento `docs/marketo-swagger-asset.json`, em Swagger 2.0: a fonte única do código gerado, com sha256 `ced6c339…` ([ADR 0004](../decisions/0004-swagger-as-single-source-with-committed-generated-code.md)). O lite-campaign fixa outra cópia, `ff7ec628…`, com 254 definições ([project intent](../intent/project-intent.md#decisões-em-aberto)).
  2. A Swagger UI que o app serve em `/api` e `/api-json` (`src/main.ts:12-18`, `README.md:39-42`). Ela sai dos controllers, não do documento. Nenhum controller tem decorators `@Api*`, e o documento servido não traz schemas: medido na #4, o `SwaggerModule.createDocument` sobre o `AssetResourcesModule` devolve 186 caminhos, 220 operações e 0 schemas.
- **tag.** Dois sentidos. Quando o sentido não é óbvio, diga "tag do Swagger" ou "tag de programa".
  1. Uma tag de operação do Swagger. A primeira tag de cada operação decide o módulo de recurso (`scripts/generate-marketo-resources.py:270`). São 23.
  2. Uma tag de programa do Marketo, do recurso `Tags`: `TagResponse`, com `tagType`, `applicableProgramTypes` e `required` (`src/asset/asset-definitions/responses/tag-response.ts:1-18`).
- **token.** Um token de programa ou de folder do Marketo, com `folderType`, `name` (até 50 caracteres), `type` (`date`, `number`, `rich text`, `score`, `sfdc campaign` ou `text`) e `value` (`src/asset/asset-definitions/requests/create-token-request.ts:1-22`). Não é o token de acesso: o Swagger de assets não tem rota de identidade, só um parâmetro `access_token` nas 33 operações v2 (a primeira em `docs/marketo-swagger-asset.json:8178`). Um token de acesso do mock é um token de mock ([project intent](../intent/project-intent.md#fora-de-escopo)).
- **Track A.** O plano do lite-campaign para o mock (R1 a R8): espaços isolados, autenticação, modelo com estado, log de requisições, falhas roteirizadas e validação estrita ([project intent](../intent/project-intent.md#critérios-de-aceite)). A [ADR 0009](../decisions/0009-behaviour-beside-generated-code.md) fica `Proposed` até a primeira sub-issue da Track A que construir comportamento, que a aceita ou a substitui.

## O loop

- **Approve.** O comentário do dono na issue cuja primeira linha é exatamente `# Owner Approve`, seguida das palavras dele. Depois dele, e só depois, o dono move a label de `ready-for-human` para `ready-for-agent`. O agente nunca faz nenhum dos dois. A palavra fica em inglês, como token ([guia](../README.md#o-approve-e-o-plano-na-issue), [ADR 0001](../decisions/0001-context-mesh-in-the-repository.md)).
- **auditoria de main.** O workflow `Auditoria de main` (`.github/workflows/main-audit.yml`, com as regras em `scripts/audit-main.mjs`). Depois do fato, confere que cada commit da linha do primeiro pai de `main` veio de uma PR mergeada que fecha uma issue, com os checks exigidos verdes e, desde `reviewRuleSince`, com a revisão do Copilot na cabeça e nenhuma thread aberta ([fluxo](../../docs/development/workflow.md#auditoria-de-main)).
- **branch empilhada.** Uma branch cortada de outra branch de issue, de um `main` local à frente do `origin/main` ou de um `claude/*`, que traz história não publicada que não é dela. O passo `stacked` do gate a recusa, e PRs nunca são empilhadas ([o passo `stacked`](patterns/loop-gate.md#o-passo-stacked), [Ciclo de vida de issue e branch](patterns/issue-branch-lifecycle.md)).
- **cabeça da PR.** O commit no topo da branch da PR (`headRefOid`). Só uma revisão do Copilot nesse commit conta, e cada push muda a cabeça ([ADR 0003](../decisions/0003-copilot-review-and-no-open-threads-before-merge.md)).
- **check exigido.** `Qualidade / check` ou `Vínculo com issue / issue-link`, nomeados por workflow e job. Nenhuma PR é mergeada com um deles vermelho ou ausente ([fluxo](../../docs/development/workflow.md#pull-requests-e-merge)).
- **dono.** O dono do repositório, `geazioliveira`. Só ele escreve o Approve e move `ready-for-agent`; o agente move `needs-triage` para `ready-for-human` quando publica um plano. Os dois postam com o mesmo login, então só a regra escrita separa esses atos ([o gate do loop](patterns/loop-gate.md#o-que-ele-não-consegue-fazer)).
- **fora do loop.** Um commit de `main` que a auditoria não liga a uma PR mergeada que fecha issue, com os checks exigidos verdes na head e, desde `reviewRuleSince`, com a revisão do Copilot e nenhuma thread aberta. Cada um vira uma issue `Mudança em main fora do loop: <sha7>` ([fluxo](../../docs/development/workflow.md#auditoria-de-main)). Os nove commits de `0c8e760` a `fb4a804` vieram antes do loop, e a auditoria não os relê: a linha de base é `8d4662f` (`auditBaseline`, `scripts/loop-sections.mjs:1233`). O registro retroativo deles é a #4.
- **gate.** `npm run gate` (`scripts/gate.mjs`). Diz quais passos do loop estão feitos, quais faltam e se o Build pode começar. Roda antes de começar e antes da PR, e em modo CI dentro do `issue-link` ([O gate do loop](patterns/loop-gate.md)).
- **Intent, Build e Learn.** Os três passos de todo trabalho, com Plan, Approve e Execute dentro do Build. Os nomes ficam em inglês, como tokens de fase ([guia](../README.md)).
- **issue de acompanhamento.** A #1, que guarda as decisões do dono sobre o harness e lista as fatias. Fica fora da regra de labels ([fluxo](../../docs/development/workflow.md#labels)).
- **issue mãe.** A issue que uma sub-issue detalha. A sub-issue nasce com `gh issue create --parent <n>` e nomeia a mãe numa seção `Issue mãe`, opcional no plano ([fluxo](../../docs/development/workflow.md#seções-que-uma-issue-precisa-ter)).
- **lane.** Um caminho de branch até `main`, com regras próprias. No lite-campaign, a lane `batch/` era o único caminho sem issue. Aqui não existe lane sem issue: toda branch é `feature/<número>-<slug>` ou `fix/<número>-<slug>` ([ADR 0001](../decisions/0001-context-mesh-in-the-repository.md), [Ciclo de vida de issue e branch](patterns/issue-branch-lifecycle.md)).
- **`# Plano`.** A primeira linha exata de um comentário que revisa o plano. O comentário traz o plano inteiro, passa a ser o plano vigente e cancela o Approve ([fluxo](../../docs/development/workflow.md#comentários-que-o-gate-lê)).
- **plano vigente.** O texto abaixo do último comentário `# Plano` da issue ou, sem nenhum, o corpo da issue. É o que os passos `sections`, `criteria` e `branch-in-plan` do gate leem ([O plano vigente](patterns/loop-gate.md#o-plano-vigente)).
- **refresh.** O workflow `Atualiza vínculo com issue` (`.github/workflows/issue-link-refresh.yml`). Roda de `main` e re-executa o `issue-link` de uma PR depois de um evento na issue, de um sinal de revisão ou de um `gh workflow run issue-link-refresh.yml --ref main -f pr=<n>`. Sozinho, não é veredito fresco ([fluxo](../../docs/development/workflow.md#pull-requests-e-merge)).
- **risco.** `HIGH` ou `NORMAL`, declarado na seção Riscos do plano. Decide a profundidade da revisão ([Revisão classificada por risco](patterns/risk-classified-review.md)).
- **sinal de revisão.** O workflow `Sinal de revisão` (`.github/workflows/review-signal.yml`). Roda em `pull_request_review`, com `permissions: {}`, e só imprime o número da PR, para o refresh re-executar o `issue-link` a partir de `main` ([ADR 0003](../decisions/0003-copilot-review-and-no-open-threads-before-merge.md)).
- **thread.** Uma thread de revisão da PR, de qualquer autor, inclusive desatualizada. É respondida (o SHA da correção, uma issue `#N` ou a evidência de que não procede) e só então resolvida. Com uma aberta, o passo `review-threads` bloqueia o merge ([fluxo](../../docs/development/workflow.md#a-revisão-do-copilot-e-as-threads), [Revisão antes do merge](patterns/review-before-merge.md)).
- **veredito fresco.** O julgamento tirado logo antes do merge: o gate em modo CI na cabeça da PR (`node scripts/gate.mjs --pr <n> --branch <branch>`) com saída 0, ou o `issue-link` da PR re-rodado (`gh run rerun <run-id>`) e acompanhado com `gh run watch <run-id> --exit-status` até sair com 0 ([fluxo](../../docs/development/workflow.md#pull-requests-e-merge)).

## Palavras a evitar

| Evite | Diga | Por quê |
| --- | --- | --- |
| "verificado", para um resultado contra o mock | "passou contra o mock" | O mock não é evidência de que algo funciona numa instância real, e um consumidor nunca o chama de "verificado" ([project intent](../intent/project-intent.md#fora-de-escopo)) |
| "sandbox", para este mock | "o mock". O nome do repositório fica como está | No Marketo, uma sandbox é uma instância real, escassa e compartilhada: é o que o mock substitui ([project intent](../intent/project-intent.md#declaração-de-intenção)) |
| "simulador", para este mock | "o mock". "Simulador" é o que um cliente escreve à mão dentro de si, como o do lite-campaign | Os simuladores escritos à mão são o problema que o mock resolve ([project intent](../intent/project-intent.md#declaração-de-intenção)) |
| "PR sem issue", "lane `batch/`" | "a issue da mudança, e a PR que a fecha" | Toda PR fecha exatamente uma issue, e não existe lane sem issue ([ADR 0001](../decisions/0001-context-mesh-in-the-repository.md)) |
| "aprovado", para um plano aceito no chat ou no plan mode | "aceito no plan mode, ainda sem Approve" | Aceitar no plan mode só autoriza postar o plano na issue, e o Approve é o `# Owner Approve` do dono (`AGENTS.md:18`) |
| "revisado", para uma PR com o CI verde | "checks verdes" | CI verde não é revisão (`docs/development/workflow.md:22`) |
| "veredito fresco", para um disparo do refresh | "refresh disparado" | O `gh workflow run` volta antes de o refresh rodar, e um refresh que falha não aparece na PR ([fluxo](../../docs/development/workflow.md#pull-requests-e-merge)) |
| "Refactor", para um commit que muda comportamento ou saída gerada | O que mudou, a começar pelo comportamento | `a967f26` se chamou "Refactor" e mudou o que o gerador emite ([Mensagem de commit que diz menos do que o commit faz](anti-patterns/commit-message-understating-its-content.md)) |
| "implementada", para uma rota que só devolve uma factory | "a rota existe e responde no formato documentado" | Os services ignoram os argumentos (`src/asset/resources/snippets/snippets.service.ts:14-17`). Comportamento é o que a Visão pede além das rotas ([project intent](../intent/project-intent.md#declaração-de-intenção)) |
| "tag", quando o sentido não é óbvio | "tag do Swagger" ou "tag de programa" | A palavra tem dois sentidos aqui (acima) |

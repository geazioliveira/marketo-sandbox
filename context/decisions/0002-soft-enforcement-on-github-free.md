# ADR 0002: Enforcement soft do loop no GitHub Free

## Contexto

- `geazioliveira/marketo-sandbox` é um repositório privado de uma conta pessoal no plano Free. Em 2026-09-24, tanto `GET repos/geazioliveira/marketo-sandbox/branches/main/protection` quanto `GET repos/geazioliveira/marketo-sandbox/rulesets` responderam HTTP 403, "Upgrade to GitHub Pro or make this repository public to enable this feature.". Nada no servidor consegue exigir um check verde, uma revisão ou uma issue vinculada antes de um merge, nem impedir um push direto em `main`.
- O dono e o agente usam a mesma conta do GitHub. Todo comentário, label e PR do agente sai com o login do dono.
- O token do `gh` não tem o escopo `project`, então o Projects v2 fica fora de alcance. Issue types só existem em organizações.
- A [ADR 0001](0001-context-mesh-in-the-repository.md) define um loop que precisa ser imposto mesmo assim.

## Decisão

O loop é imposto por camadas que se cobrem. Nenhuma delas basta sozinha.

1. **CI**, com dois checks exigidos, nomeados por workflow e job, e dois workflows que mantêm o primeiro em dia:
   - **`Vínculo com issue / issue-link`**, em `.github/workflows/issue-link.yml`, no evento `pull_request_target`. Ele roda o gate da cópia que está em `main`, por caminho absoluto e em modo CI, que falha fechado. A PR entra só como dados: nada dela é instalado nem executado. Uma PR fora do loop fica vermelha no momento em que o job roda. Desde a #13, o gate também exige, fora de draft, uma revisão do Copilot na cabeça da PR e nenhuma thread de revisão aberta (passos `copilot-review` e `review-threads`, [ADR 0003](0003-copilot-review-and-no-open-threads-before-merge.md)).
   - **`Qualidade / check`**, em `.github/workflows/check.yml`, em toda PR, em todo push em `main` e à mão (`workflow_dispatch`). Ele roda `npm ci`, depois `npm run check` (lint, `format:check`, typecheck, testes, `check:context`, build e `check:all`, nessa ordem), depois o passo `e2e` (`npm run test:e2e`), e por fim confere que a árvore ficou limpa. Numa PR, um push novo cancela a run velha; em `main`, cada commit tem o seu grupo de concorrência, então nenhuma run é cancelada nem substituída, e todo push em `main` que dispara run ganha um veredito; o que um push sem run trouxe entra na auditoria seguinte (camada 6). Desde a #9 o app não manda telemetria, então o e2e roda sem variável de ambiente. Desde a #7, o `check:all` confere que a saída gerada é a que os geradores emitem, com o python3 da imagem do runner.
   - **O refresh do `issue-link`** (workflow `Atualiza vínculo com issue`), em `.github/workflows/issue-link-refresh.yml`. Os eventos da issue não disparam o `pull_request_target`, então este workflow reage a eles: label posta ou tirada, corpo editado, fechamento e reabertura (evento `issues`), e comentário criado, editado ou apagado (evento `issue_comment`, menos os comentários de PR). Eventos de issue sempre rodam o workflow de `main`. O `scripts/refresh-issue-link.mjs` lê as PRs que fecham a issue (`closedByPullRequestsReferences`), fica só com as abertas e re-executa a run mais recente do `issue-link` de cada uma, a do SHA da head da PR, entre as runs do `issue-link.yml` no evento `pull_request_target`: uma run de outro evento, como a de um workflow que a própria PR acrescente, nunca é re-executada. Se essa run ainda está na fila ou em andamento, ele espera que ela termine, consultando-a a cada 15 s, por até 4 minutos, e só então a re-executa, porque ela pode ter lido a issue antes da mudança; se ela não termina nesse prazo, o refresh fica vermelho, com o motivo. Desde a #13, ele também tem um modo PR: responde ao `workflow_run` do sinal de revisão (abaixo), só quando a run do sinal terminou com `success`, e a um `workflow_dispatch` com o número da PR, disparado de `main` (`gh workflow run issue-link-refresh.yml --ref main -f pr=<n>`), que sozinho não é veredito fresco. Um `workflow_dispatch` roda o YAML e o script da ref em que foi disparado, então o job pula um disparo de outra ref, o que só pega acidentes. Nesse modo, o script lê a PR de novo, pula a que não está mais aberta e re-executa o `issue-link` da cabeça dela pelas mesmas regras. A única escrita é `actions: write`, para o rerun. Os Limites dizem o que ainda não foi medido.
   - **O sinal de revisão** (workflow `Sinal de revisão`), em `.github/workflows/review-signal.yml`, em `pull_request_review` (`submitted`, `dismissed`). Uma revisão não é evento do `pull_request_target`, e o evento de revisão roda o YAML da própria PR. Por isso o sinal tem `permissions: {}`, não faz checkout, não roda nada do repositório e só imprime o número da PR: quem age é o refresh, de `main`. Resolver ou reabrir uma thread não dispara workflow nenhum (Limites).

   No Free, vermelho não trava o botão de merge. Quem trava é a regra de revisão antes do merge do [fluxo de desenvolvimento](../../docs/development/workflow.md#pull-requests-e-merge): nunca mergear com um check exigido vermelho, um check ausente conta como vermelho, e logo antes do merge o veredito do `issue-link` é renovado.
2. **Gate local**, `npm run gate`: o mesmo script, no terminal, antes de começar e antes da PR. O [gate do loop](../knowledge/patterns/loop-gate.md) diz o que ele confere.
3. **Hooks do Claude Code** em `.claude/hooks/`, ligados pelo `.claude/settings.json` commitado (#5). Eles interrompem o **agente** antes que a ação aconteça, em toda sessão do Claude Code aberta neste repositório:
   - o `guard-bash` nega um comentário que abre como Approve, retirada ou título quase-Approve; `ready-for-agent` e qualquer outra escrita de label de estado, menos a troca de `needs-triage` por `ready-for-human` logo depois de um `# Plano`; `gh pr create` sem `Closes #N.`; commit e push em `main`; os tokens de skip; e resolver uma thread de revisão sem ter respondido nela, como pede a resposta 3 do dono na #13 ([ADR 0003](0003-copilot-review-and-no-open-threads-before-merge.md));
   - o `guard-bash` pede confirmação antes de `gh pr merge`, só quando os checks exigidos, a revisão do Copilot na cabeça, nenhum pedido pendente e nenhuma thread aberta estão em ordem, lidos ao vivo (senão, nega), e antes de editar o corpo da issue ou um comentário;
   - o `build-guard` só deixa editar fora de `context/intent/` com o cache do gate aberto para a branch, nega em `main` e pede confirmação num caminho do harness ou com um plano pendente;
   - o `plan-to-issue` marca como pendente o plano aceito no plan mode até ele ser publicado numa issue;
   - o `session-context` diz a branch, a issue e o estado do gate, e lembra que aprovação no chat não é Approve.

   Em `bypassPermissions`, `dontAsk` e `auto`, uma confirmação crítica vira negação. [O fluxo](../../docs/development/workflow.md#os-hooks-do-claude-code) dá os detalhes, e a saída de emergência é do dono.
4. **Forms de issue e template de PR em pt-BR**, com os headings que o gate lê, e issues em branco desligadas (`blank_issues_enabled: false`). Um form carrega um plano inteiro, então abre a issue com a label de categoria e `ready-for-human`, esperando o Approve. É orientação, não bloqueio: o dono ainda vê a opção de issue em branco, e o `gh issue create` pula os forms.
5. **Configurações do repositório**, aplicadas em 2026-09-24 com o OK do dono (pergunta 2 da #2): só merge commit (squash e rebase desligados), branch apagada no merge, e título e corpo do merge commit vindos da PR (`PR_TITLE` e `PR_BODY`), para que o `Closes #N.` chegue ao histórico de `main`. Por isso um token de pular CI escrito no título ou no corpo da PR (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` ou `[actions skip]`), ou o trailer `skip-checks: true` num último parágrafo, vai para a mensagem do merge, e o push do merge não dispara nem o `check` nem a auditoria; o [fluxo](../../docs/development/workflow.md#pull-requests-e-merge) proíbe esses tokens no título, no corpo e nas mensagens de commit da PR.
6. **Auditoria de `main`** (workflow `Auditoria de main`, job `audit`), em `.github/workflows/main-audit.yml`, depois do fato: a cada push em `main`, uma vez por dia (cron `17 6 * * *`) e à mão (`workflow_dispatch`). O job tem dois passos, os dois com o `scripts/audit-main.mjs`:
   - **O passo `Julgar`** (`auditJudgeStep`, `--judge`) lê a linha do primeiro pai de `main`, do último commit auditado até o topo, julga cada commit, abre ou comenta as issues e grava quantos commits ficaram fora do loop em `$RUNNER_TEMP/audit-verdict`. Ele termina com `success` quando julgou o intervalo inteiro, com ou sem commit fora do loop, e falha quando foi interrompido.
   - **O passo `Veredito`** (`--verdict`) lê esse número e deixa a run vermelha quando ele é maior que zero, ou quando o arquivo não existe.

   Separar os dois é o que distingue uma run vermelha que julgou o intervalo (achou commit fora do loop) de uma que não chegou a julgá-lo. O intervalo:
   - **O topo** é o `after` do push, ou o `HEAD` de `main` no agendamento e à mão.
   - **O limite de baixo** é o `head_sha` da run mais recente do `main-audit.yml` em `main`, com id menor que o da run atual, cujo passo `Julgar` terminou com `success`, lido por `GET actions/runs/{id}/jobs` (`actions: read`): só conta como auditada a run cujo passo `Julgar` terminou. Uma run interrompida, cancelada ou pulada não julgou o intervalo dela, que fica para a auditoria seguinte. Um re-run mantém o id da run, então começa da run anterior a ela e julga de novo o mesmo intervalo. A auditoria olha no máximo as 20 runs concluídas mais recentes (`auditRunsRead`).
   - **Um histórico reescrito.** Se o topo dessa run não é ancestral do topo atual, `main` foi reescrito desde ela: o topo atual fica fora do loop com o motivo `histórico de main reescrito desde a última auditoria (execução <id>, em <sha7>)`, e o intervalo começa no ancestral comum dos dois. Com o topo no clone, isso vem do `git merge-base`. Como o clone traz só as branches e as tags, um force-push costuma deixar esse topo fora dele, e então quem responde é o GitHub, por `GET repos/{repo}/compare/<topo>...<atual>` (status `diverged` ou `behind`, e o `merge_base_commit` dele).
   - **Sem ponto de partida.** Quando existem runs anteriores e nenhuma das 20 mais recentes terminou o `Julgar`, os intervalos delas nunca foram julgados, e a auditoria recomeça da linha de base, em qualquer evento (os títulos não se repetem e o teto de commits limita o intervalo). Quando não existe run anterior nenhuma, ou o topo dela não está no clone e o GitHub não o conhece mais (404 no compare), vale o `before` do push, ou a linha de base no agendamento e à mão. A saída diz sempre de onde o intervalo começou.
   - **A linha de base** é `8d4662f` (`auditBaseline`, em `scripts/loop-sections.mjs`), o merge da PR #10 da #2. Os commits alcançáveis a partir dela nunca são auditados: até `fb4a804` não havia loop, e o merge da #2 é a exceção de bootstrap, porque o `issue-link` do servidor chegou com ele e não podia estar verde nele.
   - Um merge de PR é um commit só nessa linha, e os commits da branch, já julgados na PR, não são julgados de novo.

   Por isso um push que não disparou run nenhuma (um `[skip ci]` na mensagem, um push feito com o `GITHUB_TOKEN`, uma run cancelada ou que saiu da fila) entra na auditoria seguinte, e a execução diária garante que haja uma seguinte mesmo sem outro push.

   Um commit está no loop quando é o merge commit de uma PR mergeada em `main` (o `merge_commit_sha` da PR é o commit) e essa PR:
   - fecha pelo menos uma issue deste repositório, pelas `closingIssuesReferences` ou, se nenhuma delas for deste repositório, pela primeira linha `Closes #N.` do corpo, desde que `GET repos/{r}/issues/N` confirme que #N é uma issue, e não uma PR;
   - estava com os dois checks exigidos, `Vínculo com issue / issue-link` e `Qualidade / check`, verdes no commit da head da PR na hora do merge: a run mais recente de cada job que começou antes do merge terminou com `success` antes dele. O `issue-link` só conta vindo de uma run do evento `pull_request_target` do arquivo `.github/workflows/issue-link.yml` (`issueLinkEvent` e `issueLinkWorkflowPath`), a que roda o YAML e o gate de `main`: um workflow de mesmo nome que a própria PR acrescente, ou o `issue-link.yml` disparado por outro evento, não conta. O `Qualidade / check` é achado pelo nome do workflow e do job, porque roda, de propósito, o YAML da própria PR (Limites);
   - se foi mergeada em `2026-09-25T12:00:00Z` (`reviewRuleSince`) ou depois, tinha, até o merge, uma revisão do Copilot na cabeça (`copilotReviewOn`), e não tem nenhuma thread de revisão, de qualquer autor e inclusive desatualizada, aberta até o merge e ainda não resolvida na hora da auditoria (`openThreads`), como decide a [ADR 0003](0003-copilot-review-and-no-open-threads-before-merge.md). A hora do merge e a head vêm da mesma resposta do GraphQL que as revisões e as threads. As PRs #10 e #11 foram mergeadas antes dessa data, e a #12 tratou as threads delas.

   Se o GitHub ainda não ligou o merge commit à PR, a auditoria pergunta de novo, até 3 vezes (`auditLinkRetries`), com um intervalo entre as tentativas (`AUDIT_RETRY_DELAY_MS`, 10 s por padrão), antes de dar o commit como direto. Fica fora do loop:
   - um commit direto em `main`, sem PR, como um push direto ou um commit pelo editor web;
   - o merge de uma PR que não fecha issue deste repositório;
   - o merge de uma PR sem um check exigido verde na head (`PR #P mergeada sem <workflow / job> verde`), o que inclui o merge de uma PR vermelha;
   - o merge de uma PR sob a regra de revisão sem uma revisão do Copilot na cabeça até o merge (`PR #P mergeada sem revisão do Copilot na cabeça <sha7>`), ou com uma thread de revisão aberta até o merge e ainda não resolvida (`PR #P mergeada com <n> thread(s) de revisão aberta(s)`);
   - o merge de uma PR que o GitHub mostra só em parte: mais de 100 referências de fechamento (`auditClosingPage`) sem nenhuma issue deste repositório entre as lidas, ou mais de 100 check suites na head, ou mais de 100 check runs numa suite (`auditChecksPage`); e, numa PR sob a regra de revisão, mais de 100 revisões sem nenhuma do Copilot na cabeça até o merge entre as mais recentes lidas, ou mais de 100 threads de revisão (`auditReviewPage`). A auditoria não julga o que ficou sem ler, e o motivo diz qual página veio incompleta (`PR #P: mais de 100 referências de fechamento, não lidas todas`, por exemplo). Isso não é uma interrupção: um re-run leria a mesma página, e parar ali deixaria vermelha toda auditoria seguinte, que começa do mesmo ponto. O passo `Julgar` termina com `success`, e a issue vai para o dono;
   - um force-push, e qualquer push em que o topo anterior não é ancestral do novo. O registro cai no topo novo;
   - um histórico de `main` reescrito desde a última auditoria, mesmo que o push que o reescreveu não tenha disparado run. O registro cai no topo atual, com o motivo `histórico de main reescrito desde a última auditoria (execução <id>, em <sha7>)`;
   - um intervalo com mais de 200 commits pelo primeiro pai (`auditCommitCap`). Ele é registrado uma vez, no topo, sem auditoria commit a commit.

   Para cada commit fora do loop, a auditoria abre sozinha uma issue `bug` + `needs-triage` com o título `Mudança em main fora do loop: <sha7>`, e a run fica vermelha. Com mais de 10 commits fora do loop numa auditoria (`auditIssueCap`), ela abre uma issue só, no topo, que lista todos. Abrir a issue automaticamente é a resposta 2 do dono na #3: "Vamos abrir automaticamente". Se uma issue com o mesmo título já existe, aberta ou fechada, a auditoria comenta nela a ocorrência nova (um force-push que volta `main` a um SHA antigo, por exemplo) em vez de abrir outra, e a run fica vermelha do mesmo jeito. Uma falha do `gh` ou do git interrompe o passo `Julgar`, e a run fica vermelha com o motivo e o pedido de re-rodá-la (`gh run rerun <id>`). Uma resposta do GitHub sem a hora do merge da PR, ou, numa PR sob a regra de revisão, sem a head, as revisões ou as threads, também interrompe. Como uma run interrompida não conta como auditada, o intervalo dela não se perde: o re-run o julga logo, a partir da run anterior a ela, e, sem re-run, a auditoria seguinte, a diária inclusive, o julga. As permissões são `contents: read`, `pull-requests: read`, `issues: write`, `actions: read` e `checks: read`. Cada issue é do dono, que decide registrar retroativamente ou reverter ([fluxo](../../docs/development/workflow.md#auditoria-de-main)).

### Limites

Esta decisão não finge ser mais forte do que é.

- **Os hooks param o agente, não o dono, e só onde conseguem ler.**
  - O dono os desliga com `disableAllHooks` em `.claude/settings.local.json`, e pode fazer tudo pela web ou por outro terminal.
  - Eles são do Claude Code, não do git: um `git commit --no-verify` ou um git hook não muda nada neles, e um commit feito fora do Claude Code não passa por eles.
  - Um hook que não inicia, ou que estoura o `timeout` do `.claude/settings.json`, deixa a ação seguir. O `run.sh` sai com 2 quando o script ou o `node` falta, o que bloqueia, e cada execução tem um prazo bem abaixo do `timeout`, passado o qual o hook pede confirmação crítica. O que sobra é um `node` que trava antes de o prazo começar, e isso ainda falha aberto. O `session-context` também tem prazo: passado ele, o SessionStart diz que não leu a branch e o gate a tempo, e o UserPromptSubmit, que não lê o git, sempre imprime o lembrete.
  - Um programa que o hook não consegue nomear (uma expansão herdada do ambiente) é julgado como `gh`, como `git` e como `sh`. Um avaliador como `node -e` só cai na tripwire, um arquivo passado a ele é lido como script de shell, e o que ele muda para os comandos seguintes da linha (HEAD, remotes, variáveis) não é seguido.
  - **O que o hook não lê, numa regra que nega, pede confirmação crítica,** e ela vira negação em `auto`, `dontAsk` e `bypassPermissions`. Isso vale para uma label, um `--recover`, um título, um corpo ou payload da API, um `state`, a mensagem de um commit ou de um merge e o editor do git. Só as regras que já apenas pedem confirmação (editar ou apagar um corpo ou comentário depois do Approve) ficam em confirmação simples. Em modo autônomo, isso nega os casos abaixo, e o caminho é escrever os valores literais, usar heredoc ou `"$(cat <<'EOF' … EOF)"`, ou rodar um comando por valor (um `for` com valores literais é lido uma vez por valor):
    - uma função de shell cujo argumento leva a mensagem, o corpo ou o endpoint;
    - um `xargs`, ou um laço sobre valores lidos em tempo de execução, que escreve num caminho variável;
    - um corpo reescrito na mesma linha por um programa que o hook não lê;
    - uma thread resolvida por um id que o hook não lê.
  - As mensagens que um commit traz de outro lugar (`cherry-pick`, `revert`, `am`, `commit -C`, `-c`, `--fixup`, `--squash`, `--amend`) são conferidas contra os tokens de skip. Não são lidos `merge --log`, `rebase`, `pull`, um diretório Maildir, nem um `-c include.path` que mude o `core.useReplaceRefs`.
  - `"$(cat <<EOF …)"` é lido como o heredoc enquanto o `cat` é o do sistema: um alias ou função `cat` do perfil do shell não é visto, e um definido na própria linha é.
  - O host do `gh` vem do `GH_HOST` (no comando, exportado antes na linha ou herdado) e do host de `-R` ou `GH_REPO`, no `guard-bash` e no `plan-to-issue`, que mantém o marcador quando a publicação vai para outro host ou para um host que ele não lê. O host padrão do `hosts.yml` do `gh` não é lido.
  - As leituras ao vivo vão sempre ao host do comando, que para este projeto é o github.com. São elas: o estado da PR no merge, a issue na troca de label, a thread e a conta no `resolveReviewThread`, e a confirmação de uma publicação pelo `Monitor` ou pelo terminal. Cada uma leva `--hostname`, roda com o `GH_HOST` fixado e sem `GH_REPO`, e o `GH_HOST` que o hook herdou não conta. Um comando cujo host não se lê não é lido em lugar nenhum, e a regra pede confirmação crítica. A leitura se autentica sempre com a conta que o `gh` do hook tem para aquele host, a do ambiente herdado, e nunca com um token tirado do comando.
  - **Um comando que pode rodar o `gh` com outra conta não é lido ao vivo,** porque o veredito lido com uma conta nada diz da outra: o `viewerDidAuthor`, o último autor de uma thread comparado com o `viewer`, uma PR que só ela vê. Onde o caso certo negaria (o merge, a troca de label e o `resolveReviewThread`), a regra pede confirmação crítica. O `plan-to-issue` mantém o marcador de uma publicação pelo `Monitor` ou pelo terminal; pelo Bash, a URL que o `gh` imprime continua valendo. Contam:
    - um `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` ou `GITHUB_ENTERPRISE_TOKEN` diferente do herdado, em qualquer host;
    - outro diretório de configuração do `gh` (`GH_CONFIG_DIR`, senão `XDG_CONFIG_HOME`, senão `HOME`);
    - um `gh auth login`, `logout`, `switch` ou `refresh`, ou um `gh config set`, em qualquer ponto da linha, direto ou por alias.
  - **As variáveis de conta** contam postas no comando, exportadas ou atribuídas antes na linha, ou tiradas por `env -u` ou `env -i`. Um valor com expansão conta como outro, e um vazio, como ausente. Ficam sem leitura uma troca de conta feita por um programa que o hook não lê (um script, uma extensão do `gh`), o `hosts.yml` ou o chaveiro alterados por outro meio, o `sudo`, e o ambiente do terminal do dono num `mcp__terminal__run_in_terminal`, que o hook supõe igual ao herdado.
  - **A ref de `main` só se move por PR, também fora de commit e push.** O `guard-bash` nega o `git` que escreve em `refs/heads/main`. Contam `main`, `heads/main` e `refs/heads/main`, em qualquer caixa onde o destino pode ser um sistema de arquivos que não distingue caixa, como o do macOS. Os caminhos negados são:
    - o `update-ref`, no argv e num lote `--stdin`;
    - o `branch -f`, `-m`, `-c` e `-d` de ou para `main`;
    - o `symbolic-ref` que aponta para `main` ou tira do lugar o `HEAD` do checkout de `main`;
    - o `fetch` e o `pull` com destino em `main`;
    - o `replace` de um commit da história de `main`;
    - o `checkout -B`, o `switch -C` e o `subtree --branch` para `main`;
    - o `reset` do checkout de `main` para um commit, o `rebase` e o `filter-branch` de `main`, e o `fast-import` que escreve nela;
    - o `push` para um repositório em disco que é este projeto.
  - **Uma ref, um lote ou um refspec que o `guard-bash` não lê pede confirmação crítica.** Ficam de fora da guarda da ref de `main` o `remote.*.fetch` gravado na configuração do repositório, que um `git fetch` sem refspec segue (o próprio `git` recusa buscar para a branch com checkout no checkout do dono), o `send-pack`, o `rebase --update-refs`, o `stash branch`, o `checkout --orphan` e as tags.
  - **Os parâmetros que o `gh api` põe na query string contam como campos do corpo.** Com `--input`, o `gh` manda os `-f` e `-F` na query string, e o que o endpoint escreve depois de `?` vai junto. O `guard-bash` os julga pelas regras dos campos do corpo, por cima e por baixo dele, porque não se mediu se o GitHub os lê nem qual dos dois vale. Um parâmetro repetido com valores diferentes, ou cuja chave ele não lê, pede confirmação crítica. O achatamento das chaves aninhadas (`x[state]=open` vai como `state=open`) foi medido no `gh` 2.101.
  - **O repositório do `gh` sai do `GIT_DIR` que o comando vê,** no comando, exportado antes na linha ou herdado, no `guard-bash` e no `plan-to-issue`. Um `GIT_DIR` com expansão, ou que não aponta para um repositório que o hook leia, mantém o marcador, e o hook diz por quê. O `GIT_WORK_TREE` não muda o repositório (medido no git 2.50 e no gh 2.101), e o `GIT_COMMON_DIR` não é seguido.
  - **A configuração que o comando dá ao `git` também decide o repositório do `gh`,** no `guard-bash` e no `plan-to-issue`. Contam `GIT_CONFIG_COUNT` com `GIT_CONFIG_KEY_n` e `GIT_CONFIG_VALUE_n`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG`, `HOME` e `XDG_CONFIG_HOME`, postas no comando, exportadas ou atribuídas antes na linha, ou tiradas com `env -u` ou `env -i`. Com elas, os remotes são lidos de novo com exatamente esse ambiente, e só vale uma configuração que o hook lê inteira. O repositório fica desconhecido com:
    - um valor com expansão ou vazio, ou um `GIT_CONFIG`;
    - um include, um `insteadOf` ou um `gh-resolved`;
    - outro remote além do `origin`, uma URL de push dele, ou um `origin` com URLs de mais de um repositório;
    - uma configuração que o `git` recusa, ou uma linha que mudou os remotes antes.
  - **Um repositório desconhecido por configuração** é julgado como este projeto para negar, com confirmação crítica antes de qualquer leitura ao vivo, e mantém o marcador no `plan-to-issue`. Uma atribuição solta de `GH_*`, `GIT_*`, `GITHUB_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `HOME` ou `XDG_CONFIG_HOME` conta como desconhecida, porque o hook não sabe se o shell a exporta. O ambiente herdado segue como antes: é o mesmo do hook. O `sudo`, que troca o ambiente, não é seguido.
  - O `plan-to-issue` falha fechado no `ExitPlanMode`. Qualquer falha ao marcar o plano aceito cai num caminho de reserva que grava o marcador no diretório git comum do cwd, numa fatia do prazo guardada para isso. Isso vale para uma biblioteca que não carrega, o prazo que acaba enquanto ele lê o repositório, um diretório do git sem escrita ou um defeito. Se nem assim o marcador é gravado, ele remove o cache do gate de cada worktree do repositório. Antes de gravar ou remover, ele lê o `origin` no arquivo de config do repositório: num repositório de outro projeto, de outro host ou sem `origin`, não mexe em nada, e um `origin` que ele não lê conta como este projeto (#40). Um include ou um `insteadOf` não é seguido ali. Em todos os casos, diz ao Claude pelo stderr, com saída 2, o que fez, ou que nada foi gravado e que não se constrói. Numa publicação, uma falha nunca remove o marcador. Sobram três buracos, cobertos só pela mensagem:
    - sem o marcador, um `npm run gate` rodado de novo reabre o gate sobre o Approve antigo;
    - um cache que não se remove deixa o gate aberto naquele worktree;
    - um `git` que trava também no caminho de reserva não deixa gravar nada.
  - Um script por pipe, por arquivo ou por `sh` só é julgado quando a linha cita `gh` ou `git`; a tripwire julga um avaliador ilegível pelos nomes que a linha escreve; as extensões do `gh` rodam sem leitura.
  - Um `git push` com `--repo` e um repositório na linha é julgado pelas duas leituras, e a pior vale.
  - O `settings.local.json` do usuário é protegido em qualquer lugar, mas o `~/.claude/settings.json` não, e ele também pode ligar o `disableAllHooks`.
  - Eles não leem um programa rodado a partir de um arquivo (`./script.sh`, `node script.mjs`, `npm run`). O `build-guard` cobre `Edit`, `Write` e `NotebookEdit`. O `guard-bash` cobre as escritas pelo shell nos arquivos do loop e nos caminhos do harness, e as escritas do `git` nos arquivos do worktree e no índice: `checkout` e `restore` de caminhos, `reset --hard`, `--merge` e `--keep`, `apply`, `am`, `cherry-pick`, `revert`, `merge`, `pull`, `rebase`, `stash apply`, `pop` e `branch`, `rm`, `mv`, `clean`, `read-tree`, `checkout-index` e as demais. Essas escritas recebem a mesma decisão que o `build-guard` dá a uma edição dos mesmos arquivos (`.claude/hooks/lib/edit-gate.mjs`). Uma escrita num arquivo comum por outro programa do shell (`>`, `tee`, `cp`, `sed -i`, um script) com o gate fechado continua sem leitura, por um link ou não.
  - **Uma escrita pelo shell é julgada onde cai.** O `guard-bash` segue cada link simbólico do caminho, o último e os pendentes inclusive, com o mesmo `placeOf` (`.claude/hooks/lib/repo.mjs`) que o `build-guard` usa numa edição. Ele julga o caminho escrito, o destino e a própria entrada, e vale o pior: por isso um `rm` ou um `sed -i` de um link para um arquivo do loop também é recusado. Segue ainda os links que a linha cria antes da escrita e que o disco ainda não tem: `ln` (simbólico ou físico), `link`, `cp -s`, `cp -l`, e o link que `cp`, `mv`, `rsync` e `ditto` carregam, inclusive dentro de `bash -c` e de `$(…)`. Criar um link físico para um arquivo do loop conta como escrever nele. Um link cuja origem tem expansão deixa o destino desconhecido: o hook nega quando o texto nomeia um arquivo do loop e pede confirmação crítica no resto. Ficam sem leitura:
    - um link criado na linha por outro programa (um `tar`, um `unzip`, um `git checkout`, um interpretador), seguido só a partir da linha seguinte, quando já está no disco;
    - um link físico criado fora de uma linha lida, que não se distingue de um arquivo comum.
  - Ficam de fora da decisão do gate as escritas do `git` de que o loop precisa antes de ele abrir: criar ou trocar de branch sem caminho, `fetch`, as leituras, `stash push`, `list`, `show` e `drop`, `worktree add`, os `--dry-run`, os `--abort`, `add`, `commit`, `reset --soft` e `--mixed` sem caminho, e um `merge --ff-only` para `main`, que deixa o worktree onde uma troca para `main` deixaria.
  - Uma escrita do `git` que não nomeia caminho (`merge`, `pull`, `rebase`, `stash pop`, `cherry-pick`, `am`, `reset --hard`) é julgada como o worktree inteiro. Com o gate aberto, os arquivos que ela traz não são lidos: um caminho do harness entre eles não pede confirmação. O mesmo vale, com o gate aberto, para um caminho que o hook não lê (uma variável, um glob) e para o worktree inteiro (`.`). Um diretório nomeado que contém caminhos do harness pede confirmação, e um `git clean -x` ou `-X` que alcança o `.claude/settings.local.json` é negado (#37). Com o gate fechado, a dúvida pede confirmação crítica, e um `git rebase --continue` é negado, porque roda com a HEAD solta.
  - O projeto é reconhecido pelo `origin`, inclusive quando um comando anterior da mesma linha o muda: num clone sem `origin`, ou com o remote renomeado, os hooks passam, e quando o `gh` escolhe outro remote que não o `origin` (o padrão de `gh repo set-default`, por exemplo), eles julgam pelo `origin`. Isso vale para o ambiente herdado; com uma configuração própria do comando, outro remote ou um `gh-resolved` deixam o repositório desconhecido.
  - O marcador de plano pendente é da sessão que aceitou o plano: uma sessão nova não o herda. O nome do arquivo codifica o id da sessão sem colisão (`[A-Za-z0-9-]` como está, cada outro byte UTF-8, `_` inclusive, como `_XX`), então a publicação de uma sessão nunca remove o marcador de outra; um id UUID, o que o Claude Code usa, mantém o nome de antes. Pelo `Monitor` e pelo terminal, o `plan-to-issue` só o tira com a URL na saída ou com a confirmação ao vivo do GitHub: um comando que ainda não terminou, um relógio fora de hora ou uma issue fora das 20 mais novas da conta mantêm o marcador.
  - **O critério do agente cooperativo** (plano da #5, Approve de 2026-09-28). Os hooks param o agente que segue o loop e erra, não o que prepara o terreno para passar por eles. Um achado de revisão que só acontece com evasão deliberada fica aqui, e a resposta da thread o cita. Um achado que um agente honesto ou o dono podem cometer vira correção, com teste. Ficam como limites:
    - da décima revisão da PR #26: um arquivo do loop escrito pelo shell com outra caixa (`LOOP-GATE.JSON`), num disco que não distingue caixa, e uma linha montada para demorar no parser até estourar o prazo do hook;
    - no parser de shell (PR #43):
      - `source` e `.`, porque a linha é lida, não o arquivo que ela roda;
      - um `env -u` com o nome numa expansão, e `exec -c`;
      - mais de 64 wrappers aninhados;
      - o argv que o `xargs` monta do stdin, e o `--process-slot-var` dele;
      - um executável num caminho exótico, e um glob sem aspas, um `~usuário` ou um `=cmd` do zsh no lugar do comando;
      - uma construção composta sem fechamento, que o bash nem roda;
      - `export -n`, e um `cd` dentro da definição de uma função;
      - as opções com valor do `time` do GNU antes do comando;
    - no `build-guard` e na leitura do repositório (PRs #42 e #44):
      - um caminho que atravessa um link simbólico e volta (`link/../arquivo`), normalizado antes de o link ser seguido;
      - o `.claude` do worktree como link simbólico para fora, que o deny de `Edit(//**/.claude/settings.local.json)` cobre pelo caminho escrito;
      - um arquivo ignorado pelo git, que o gate não cobre por desenho (um caminho do harness nunca passa por ser ignorado);
    - nas regras de git (PR #45):
      - um `PATH` ou `GIT_EXEC_PATH` do comando que aponta para um `git` falso, um `true` falso como `GIT_EDITOR`, um `git-<nome>` externo no `PATH` e o `git hook run`;
      - aliases trocados entre comandos da mesma linha por `GIT_CONFIG_COUNT`;
      - `send-pack`, `subtree push` e um push para `file://localhost/` com este projeto, para `main`;
      - `merge --log` com `GIT_EDITOR=true` e um assunto com token de pular CI preparado numa branch, e `GIT_MERGE_AUTOEDIT` numa expansão;
      - uma cadeia de refs simbólicas até `main`, `checkout --orphan main` e `switch --orphan main` (o commit e o push em `main` seguem negados), e `filter-branch --state-branch main`;
      - comandos em `rebase --exec` e nos filtros do `filter-branch`;
      - a saída de `archive`, `format-patch -o` e `bundle create` apontada para o harness, `worktree remove`, `submodule`, e `subtree add`, `pull` e `merge`;
      - o stdin de um `git -C` lido no diretório do `-C`, com dois arquivos de mesmo nome preparados, e `--no-replace-objects` com um objeto de substituição preparado;
      - o verbo do `sparse-checkout` ou do `worktree` numa expansão;
    - nas regras do `gh` (PR #47):
      - o `AppData` do Windows trocado no comando;
      - `gh issue create --template` com um modelo que abre como Approve, que teria de estar em `main` (e o gate só lê o Approve nos comentários);
      - a ref de `main` codificada na rota REST (`heads%2Fmain`), e as mutações GraphQL que escrevem ref ou commit em `main` (`createCommitOnBranch`, `updateRef`, `deleteRef`), que a auditoria de `main` pega depois;
      - a URL de um GitHub Enterprise tomada como este projeto, cuja escrita vai para outro host;
    - no `guard-bash` (PR #52):
      - um programa rodado a partir de um arquivo (`node x.mjs`, `python3 -m`) não é avaliador nem escrita que o hook não vê: tratá-lo assim pediria confirmação em `node scripts/gate.mjs` e nos geradores;
      - uma escrita no harness por um interpretador (`python3 -c "open('.claude/hooks/…', 'w')"`) não cai na tripwire: casar `.claude/` no texto pegaria todo comando num worktree em `.claude/worktrees/` e todo o que cita `~/.claude/`;
    - no `plan-to-issue` (PR #54): um `gh` falso no `PATH` do comando, que imprime a URL de uma publicação que não houve.
  - **Um falso positivo conhecido:** um heredoc seguido de `&&`, `||` ou `|` na mesma linha não se lê, e o hook pede confirmação.
- **O dono consegue mergear com vermelho ou dar push direto em `main`.** Nenhuma camada impede o dono. A auditoria de `main` registra depois do fato o push direto, o commit pelo editor web, o force-push e o histórico reescrito, o merge de uma PR que não fecha issue e o merge de uma PR sem os checks exigidos verdes, mas não desfaz nenhum deles.
- **A auditoria roda o YAML que está em `main`.** Um push direto que muda ou apaga o `main-audit.yml` é julgado pela cópia que ele deixou, e as auditorias seguintes, a diária inclusive, rodam essa mesma cópia até alguém restaurá-la pelo loop. O push continua no `git log`.
- **Uma reescrita só é nomeada enquanto o GitHub conhece o topo auditado.** Quando um force-push deixa o topo da última run auditada fora do clone, a auditoria pergunta ao GitHub pelo compare. Só se o GitHub também não o conhece mais (404) ela não nomeia a reescrita: num push, começa do `before` dele, e o que o force-push trouxe antes desse `before` não é julgado; no agendamento e à mão, recomeça da linha de base e comenta outra vez nas issues de mesmo título que já existem.
- **Um merge que o GitHub demora a ligar à PR vira issue.** Se, depois das 3 tentativas, o GitHub ainda não devolve a PR de um merge commit, esse merge é registrado como commit direto: o dono fecha essa issue citando a PR. E a issue de mesmo título é achada pela busca de issues, que tem atraso: um rerun logo depois da primeira run pode abrir uma issue repetida.
- **O gate não sabe quem escreveu um Approve.** Agente e dono postam com a mesma conta, então um Approve escrito pelo agente em nome do dono é idêntico a um do dono. Numa sessão do Claude Code deste projeto, os hooks da #5 impedem o agente de escrever um Approve; fora delas, só a regra escrita. O gate a imprime em toda execução.
- **Os hooks só valem para sessões do Claude Code que carregam as configurações deste projeto.** Outra ferramenta, outro agente ou uma sessão com os hooks desligados passa ao largo. Numa sessão deste projeto, eles seguem o `.claude/settings.json` do checkout da sessão. Trocar esse worktree para uma branch que não tem o arquivo, de antes da #5, os desliga até a troca de volta, como a primeira tentativa de uma sonda da #5 mostrou.
- **Um `issue-link` verde ainda pode envelhecer.** O `pull_request_target` só reage a eventos da PR. Desde a #3, o refresh re-executa o `issue-link` quando a issue muda, mas:
  - ninguém mediu ainda se o `GITHUB_TOKEN` consegue re-executar uma run de `pull_request_target`. O `issue-link` não tinha nenhuma run no servidor quando o refresh foi escrito, e a primeira prova é o primeiro evento de issue depois do merge da #3. Se o rerun for recusado, o refresh fica vermelho, e esta decisão ganha uma linha `Atualizado` com o que se mediu;
  - uma run do `issue-link` ainda na fila ou em andamento é consultada a cada 15 s (`REFRESH_POLL_MS`), esperada por até 4 minutos (`REFRESH_WAIT_MS`) e só então re-executada. Se ela não termina nesse prazo, o refresh fica vermelho sem re-executá-la, e só o veredito fresco cobre esse caso;
  - o GitHub re-executa uma run no máximo 50 vezes, e só até 30 dias depois de ela começar. Depois disso, o refresh fica vermelho, e um push na PR traz uma run nova;
  - um rerun reusa o SHA de `main` da run original, então roda o gate como ele estava em `main` quando a run começou, não o de hoje;
  - vincular uma issue pela barra lateral da PR não é evento da issue nem da PR, e não roda nada.

  Por isso a regra de merge do [fluxo](../../docs/development/workflow.md#pull-requests-e-merge) continua exigindo um veredito fresco logo antes do merge, de um destes dois jeitos: rodar `node scripts/gate.mjs --pr <p> --branch <branch>` na head da PR e exigir saída 0, ou re-rodar o job `issue-link` da PR (`gh run rerun <run-id>`) e acompanhá-lo até o fim com `gh run watch <run-id> --exit-status`, também com saída 0. Um disparo do refresh sozinho não é veredito fresco: o comando volta antes de o refresh rodar, e um refresh que falha não aparece na PR. A regra fica pelo menos até o refresh ser provado ao vivo. Só uma linha `Atualizado` desta decisão, com a medição, pode afrouxá-la, e os casos acima que o refresh não cobre continuam com ela.
- **A revisão do Copilot e as threads têm limites próprios** ([ADR 0003](0003-copilot-review-and-no-open-threads-before-merge.md)):
  - resolver ou reabrir uma thread não dispara workflow nenhum (`pull_request_review_thread` só existe como webhook). Depois de resolver, o agente atualiza o check com `gh workflow run issue-link-refresh.yml --ref main -f pr=<n>`, que sozinho não é veredito fresco, e logo antes do merge tira o veredito fresco (acima). Sem isso, o `issue-link` fica com o veredito de antes: vermelho, o lado seguro, quando a última thread foi resolvida, e verde velho quando alguém reabre uma;
  - o sinal roda o YAML da própria PR, e uma PR consegue mudá-lo ou apagá-lo. Ela não consegue afrouxar o veredito, porque o sinal não julga nada e o refresh vem de `main`, mas consegue deixá-lo velho: sem o sinal, uma revisão nova ou dispensada não re-executa o `issue-link`. O veredito fresco antes do merge e a auditoria cobrem esse verde velho;
  - a revisão do próprio Copilot dispara `pull_request_review`, mas a run do sinal fica em `action_required`: o GitHub pede aprovação para uma run disparada por bot (medido na PR #15, run 36162828374, ator `Copilot`, tipo `Bot`). Então o refresh não roda sozinho depois da revisão do Copilot (e um refresh sozinho não é veredito fresco): o veredito é renovado à mão, como pede a regra do veredito fresco;
  - uma thread apagada some: quem apaga o comentário que a abriu (o dono, ou o agente, que posta com a conta dele) a tira do gate e da auditoria, e nada registra isso;
  - o GitHub não guarda quando uma thread foi resolvida (não existe `resolvedAt`). A auditoria julga as threads como estão na hora dela, segundos depois do push do merge: uma thread resolvida entre o merge e a auditoria passa, e uma reaberta depois da auditoria não é vista;
  - quem resolveu e por quê não se conferem: `resolvedBy` é sempre o login do dono, e o motivo (`ADDRESSED`, `WONT_FIX` ou `INVALID`) não se lê de volta. Numa sessão do Claude Code deste projeto, o `guard-bash` nega resolver uma thread cujo último comentário não é de quem resolve; fora delas, responder antes de resolver é regra escrita;
  - um achado que aparece só no resumo da revisão, sem thread, não é lido pelo gate nem pela auditoria. O agente o trata na PR;
  - uma revisão do Copilot que falhou chega como `COMMENTED`, do bot, na cabeça. O gate e a auditoria só a reconhecem pelo começo do corpo, pelos textos de falha que o contrato conhece (`copilotFailedReview`), ou por um corpo ausente, vazio ou só com espaços: um texto de falha novo passaria como revisão até entrar no contrato.
- **Só o `issue-link` resiste à própria PR.** O `check.yml` (workflow `Qualidade`, job `check`) roda em `pull_request`, com o YAML e o `package.json` da própria PR. Uma PR consegue tirar um passo do `npm run check` ou do YAML e continuar com um `check` verde, ou acrescentar outro workflow chamado `Qualidade` com um job `check`, que a auditoria acha pelo nome e não distingue do verdadeiro. Por isso os checks exigidos são nomeados por workflow e job (`Qualidade / check` e `Vínculo com issue / issue-link`), e uma PR que toca `.github/workflows/**` é de risco HIGH na revisão. O `issue-link` não tem esse buraco: a auditoria só o aceita de uma run do evento `pull_request_target` do `.github/workflows/issue-link.yml`, o refresh só re-executa essas runs, e o refresh roda de `main`, como o `issue-link`.
- **Minutos de Actions.** O repositório é privado no Free, com minutos contados. Cada label, comentário ou edição numa issue gasta um runner do refresh, por mais tempo quando ele espera uma run em andamento, até o job parar aos 5 minutos; cada push em `main`, cada dia e cada disparo à mão gastam um da auditoria; cada PR e cada push em `main` gastam um do `check`; cada revisão enviada ou dispensada numa PR gasta um do sinal e outro do refresh, e cada resposta numa thread é uma revisão enviada (`COMMENTED`, de quem responde), então cada resposta também gasta um do sinal e um do refresh.
- **PRs de fork ficam vermelhas, de propósito.** Em `pull_request_target`, o `actions/checkout` v7 recusa a head de um fork enquanto `allow-unsafe-pr-checkout` fica desligado. Toda mudança nasce numa branch deste repositório.
- **Os forms são pulados pelo `gh issue create`.** O que segura a forma do plano é o passo `sections` do gate, não o form.

### Caminho de upgrade

Se o repositório passar para Pro, Team, uma organização, ou ficar público, um ruleset em `main` torna `issue-link` e `check` obrigatórios e bloqueia o push direto. Nesse dia, esta decisão ganha uma linha `Atualizado` dizendo o que virou regra do servidor.

## Racional

Cada camada cobre um buraco de outra:

- o `issue-link` não pode ser afrouxado por quem abre a PR, mas não bloqueia o merge;
- o refresh renova o `issue-link` quando a issue muda, mas o rerun ainda não foi provado ao vivo e não cobre todos os casos;
- o sinal de revisão avisa o refresh quando uma revisão chega, mas roda o YAML da própria PR, então não tem permissão nenhuma e não julga nada;
- o `check` pega uma regressão no código, nos testes, no build e no `context/`, mas a própria PR consegue afrouxá-lo;
- o gate local é rápido e dá o veredito fresco, mas é opcional;
- os hooks param o agente antes da ação, mas não o dono, e só nas sessões do Claude Code deste projeto;
- os forms guiam quem abre pela web, mas não bloqueiam nada;
- a auditoria de `main` registra o que chegou fora do loop, o merge de uma PR vermelha inclusive, mas só depois do fato, e roda a cópia do YAML que está em `main`.

Empilhadas, elas fazem o caminho certo ser o mais fácil e deixam qualquer desvio visível, sem custo e sem conta nova. O gate do `issue-link` vem de `main` para que uma PR não consiga afrouxar esse check. O `check` não tem essa proteção, e é por isso que a revisão trata como HIGH uma PR que mexe nos workflows.

A auditoria lê a linha do primeiro pai de `main` desde o último commit auditado, e ignora a história até `8d4662f`. Começar da última run cujo passo `Julgar` terminou, e não do `before` do push, é o que cobre um push que não disparou run e uma run interrompida; a execução diária cobre o dia em que nenhum push chega. Separar `Julgar` de `Veredito` é o que deixa contar como auditada uma run vermelha que julgou tudo, e não uma que parou no meio. Começar do `merge-base` quando `main` foi reescrito é o que faz uma reescrita sem run virar issue, em vez de sumir entre duas auditorias. O primeiro pai evita julgar de novo os commits de uma branch que a PR já julgou, e a linha de base evita uma issue para cada commit anterior ao loop. Conferir os checks exigidos na head da PR é o que pega o merge de uma PR vermelha, que antes só a regra de revisão pegava, e exigir o `issue-link` do `pull_request_target` é o que impede a própria PR de trazer um verde falso para ele. Ela abre a issue sozinha, em vez de só ficar vermelha, porque assim toda mudança em `main` termina ligada a uma issue.

## Alternativas consideradas

| Opção | Por que não |
| --- | --- |
| GitHub Pro | O dono recusou o custo |
| Tornar o repositório público | O código é privado |
| Git hooks locais (husky) | Ficam numa máquina só, `git commit --no-verify` os pula, e eles não enxergam issue nem Approve |
| Um GitHub App ou bot com conta própria | Resolveria a autoria do Approve, mas é infraestrutura demais para um mock com um dono só |
| Projects v2 para o estado do trabalho | O token não tem o escopo `project`, e um board não impõe nada |

## Consequências

- **Mais fácil**: o loop funciona sem custo e sem conta nova. Cada camada é testável sozinha, e as regras que nenhuma camada impõe estão escritas. Uma regressão no código ou no `context/` deixa a PR vermelha, e um commit que chega em `main` fora do loop vira uma issue sem que ninguém precise ler o `git log`.
- **Mais difícil**: o merge depende de disciplina. Um CI vermelho precisa ser lido, e mergear com vermelho é uma violação que a revisão precisa pegar antes: a auditoria de `main` só a registra depois. Até o refresh ser provado ao vivo, um verde também precisa ser renovado à mão antes do merge. O dono precisa lembrar de não dar push em `main`, e cada push fora do loop deixa uma issue para ele triar. O refresh e a auditoria gastam minutos de Actions contados (Limites). Desde a #13, cada merge também espera uma revisão do Copilot na cabeça e nenhuma thread aberta, e resolver uma thread pede renovar o veredito à mão ([ADR 0003](0003-copilot-review-and-no-open-threads-before-merge.md)).
- Como o CI roda o gate de `main`, uma PR que corrige o gate é julgada pelo gate antigo até ser mergeada.
- A PR da #2, que cria o `issue-link`, não tem esse check no servidor, porque o workflow ainda não está em `main`. Só nela, a saída do gate em modo CI rodado localmente, colada na "Verificação", faz as vezes do `issue-link`, e o veredito fresco antes do merge é essa mesma execução refeita. A primeira execução real é na PR da #3.
- A PR da #3 cria a auditoria e o refresh, e os dois só rodam a partir de `main`. A primeira auditoria é a do merge dessa PR: sem run anterior, ela começa do `before` do push, e não deve abrir issue. Isso vale se nem o título nem o corpo dessa PR levam um token de pular CI, que iria para a mensagem do merge (camada 5); com um deles, a primeira auditoria seria a diária, e o merge ficaria sem a sua run do `Qualidade / check` em `main`. O primeiro refresh é o primeiro evento de issue depois desse merge.

# Hooks do Claude Code (#5)

Hooks de projeto que interrompem, antes da ação, os atalhos do loop issue-first: o Approve escrito pelo agente, uma label de estado fora da única troca permitida, código editado sem o gate aberto, PR sem issue, merge com a revisão velha. O plano e os critérios estão em `context/intent/feature-claude-code-hooks.md`.

| Script                | Evento                                                                           | O que faz                                                                              |
| --------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `guard-bash.mjs`      | PreToolUse `Bash\|Monitor\|mcp__terminal__run_in_terminal`                       | Nega ou pede confirmação para comandos `gh` e `git` que contornam o loop               |
| `build-guard.mjs`     | PreToolUse `Edit\|Write\|NotebookEdit`                                           | Só deixa escrever fora de `context/intent/` com o gate aberto para a branch            |
| `plan-to-issue.mjs`   | PostToolUse `ExitPlanMode`, `Bash`, `Monitor` e `mcp__terminal__run_in_terminal` | Marca o plano aceito como pendente até ele ser publicado numa issue                    |
| `session-context.mjs` | SessionStart e UserPromptSubmit                                                  | Diz a branch, a issue e o estado do gate, e lembra que aprovação no chat não é Approve |

`lib/` guarda o que os quatro compartilham. `lib/edit-gate.mjs` é a decisão do gate para uma escrita no worktree: o `build-guard` a pede para o arquivo que o Edit ou o Write escreve, e o `guard-bash` (por `lib/git-rules.mjs`) para os arquivos que um comando `git` escreve (`git checkout -- arquivo`, `git restore`, `git merge`…). `lib/plan-publication.mjs` é o trabalho do `plan-to-issue`, carregado dentro de um `try`: se uma biblioteca não carrega, ou se marcar um plano aceito falha por qualquer motivo (o prazo acabou lendo o repositório, o diretório do git não aceita escrita, um defeito), o hook grava o marcador por um caminho curto, numa fatia do prazo guardada para isso; se nem assim consegue, remove o cache do gate de cada worktree do repositório, e o `build-guard` lê o gate como não rodado. Numa publicação, uma falha nunca remove o marcador. Em todos esses casos, o hook diz ao Claude pelo stderr, com saída 2, o que fez, ou que nada foi gravado e que não se constrói. Os contratos do loop vêm de `scripts/loop-sections.mjs`, a mesma fonte do gate e da auditoria. Os testes ficam em `test/hooks/`, e cada um roda o hook como processo, com a entrada em JSON no stdin.

Os hooks só restringem: nunca devolvem `allow`. Na dúvida, pedem confirmação (`ask`), e em `bypassPermissions`, `dontAsk` ou `auto` o `ask` crítico vira `deny`.

Cada execução tem um prazo só (`lib/budget.mjs`), dividido por todos os `git` e `gh` que ela roda e bem abaixo do `timeout` do hook no `settings.json`: passado o prazo, o hook pede confirmação, crítica, antes que o Claude Code o mate e deixe a ação passar sem decisão. O `session-context` também tem o seu: quando ele acaba, ou um `git` estoura o próprio tempo, o SessionStart diz que não conseguiu ler a branch e o gate a tempo, e o lembrete do UserPromptSubmit sai sempre, porque não lê o git. `LOOP_HOOKS_BUDGET_MS` só baixa o prazo, para os testes.

O repositório de um comando `gh` sai dos remotes que o `git` lê com a configuração que o hook herdou, a mesma que o comando herda. Um comando que dá ao `git` uma configuração própria (`GIT_CONFIG_COUNT` com `GIT_CONFIG_KEY_n` e `GIT_CONFIG_VALUE_n`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG`, `HOME` ou `XDG_CONFIG_HOME`, no comando, exportada antes na linha, atribuída antes na linha ou tirada por `env -u` ou `env -i`) é lido de novo com exatamente esse ambiente, no `guard-bash` e no `plan-to-issue`. Só conta uma configuração que o hook lê inteira: um valor com expansão, um include, um `insteadOf`, um `gh-resolved`, outro remote além do `origin` ou um `origin` com mais de um repositório deixam o repositório desconhecido, julgado como este projeto para negar e nunca para passar.

Uma escrita pelo shell é julgada onde cai, com o `placeOf` de `lib/repo.mjs`, o mesmo que o `build-guard` usa numa edição: cada link simbólico do caminho é seguido, o último e os pendentes inclusive, e vale o pior entre o caminho escrito, o destino e, quando a entrada é um link, o próprio link, que o `sed -i` e o `rm` trocam ou tiram. O `guard-bash` também segue os links que um comando anterior da mesma linha criou e que o disco ainda não tem: `ln` (simbólico ou físico), `link`, `cp -s`, `cp -l`, e o link que `cp`, `mv`, `rsync` e `ditto` copiam ou movem. Um link que uma substituição ou um script de `bash -c` cria conta também para os comandos listados antes dele, porque ele roda antes do comando que o contém; como a ordem não se sabe, o que a linha lê por esse link fica desconhecido. O que a linha escreveu num arquivo fica guardado pelo lugar onde a escrita cai, para o corpo que um comando seguinte lê; dois nomes escritos que só diferem nas maiúsculas deixam o conteúdo desconhecido. Criar um link físico para um arquivo do loop é julgado como escrever nele. Um `$PWD` no começo de um caminho é o diretório do comando, a menos que a linha dê outro valor ao `PWD`, em qualquer grafia (`read P''WD`).

As leituras ao vivo do GitHub vão ao host para onde o comando vai, nunca ao `GH_HOST` que o hook herdou: este projeto fica no github.com, e cada leitura leva `--hostname github.com`, com `GH_HOST` fixado e sem `GH_REPO`. Um comando cujo host não se lê (uma expansão em `GH_HOST` ou `--hostname`) não é lido em lugar nenhum: a regra pede confirmação, crítica.

A leitura se autentica sempre com a conta do hook, a do ambiente que ele herdou, e nunca com um token tirado do comando. Um comando que pode rodar o `gh` com outra conta também não é lido, e a regra pede confirmação crítica: é o que acontece quando ele vê um `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` ou `GITHUB_ENTERPRISE_TOKEN` diferente do herdado, ou outro diretório de configuração do `gh` (`GH_CONFIG_DIR`, senão `XDG_CONFIG_HOME`, senão `HOME`, lido a partir do diretório do comando; um relativo depois de um `cd` que não se lê conta como outro), seja no comando, exportado ou atribuído antes na linha, ou tirado por `env -u` ou `env -i`, e quando a linha tem um `gh auth login`, `logout`, `switch` ou `refresh`, ou um `gh config set`, em qualquer posição. No `plan-to-issue`, uma publicação pelo `Monitor` ou pelo terminal nesses casos não é conferida no GitHub, e o marcador continua.
